\begin{center}
  {\Large\bfseries\underline{ABSTRACT}\par}
\end{center}
\vspace{1cm}
\projectname{} is a small web-based music library for sharing audio, listening in the browser, and giving feedback. It uses Flask, vanilla JavaScript, and MariaDB/MySQL. Users can register, upload tracks, and submit one editable rating and review per song.

\chaptertitle{Introduction}

\subsection{Project}
\projectname{} focuses on three essential interactions: sharing a track, listening to it, and receiving feedback. Its small scope keeps the workflow clear while the relational database preserves ownership and rating integrity.

\subsection{Aim and objectives}
The project provides a community music library with authenticated participation. Its objectives are to:
\begin{itemize}[leftmargin=*]
  \item allow visitors to browse available songs and play audio in a web browser;
  \item allow new users to register and existing users to log in and log out;
  \item allow authenticated users to upload a song with a title and artist name;
  \item allow authenticated users to rate a song from one to five stars and add an optional review;
  \item prevent duplicate ratings from the same user for the same song; and
  \item store passwords and uploaded-file paths safely.
\end{itemize}

\subsection{Scope of the project}
The scope includes accounts, song metadata, local audio storage, playback,
ratings, reviews, administration, and a responsive interface. Playlists,
search, moderation, and cloud storage are outside the current scope.

\subsection{Database Management System}
The project uses a relational database management system to store users, songs, and ratings in related tables. Primary keys identify records, foreign keys preserve relationships, and constraints protect data integrity. Parameterized SQL queries are used by the Flask application to communicate with MariaDB or MySQL.

\subsection{Functional requirements}
\begin{enumerate}[leftmargin=*]
  \item A visitor shall be able to view the song library.
  \item A visitor shall be able to register with a unique username and password.
  \item A registered user shall be able to log in and log out.
  \item An authenticated user shall be able to upload a song title, artist name, and audio file.
  \item A visitor shall be able to play an uploaded song using the browser audio controls.
  \item An authenticated user shall be able to submit a one-to-five-star rating and optional review.
  \item A later rating submission shall update the user's existing rating for that song.
  \item The library shall show each song's average rating and rating count.
  \item An administrator shall be able to review and manage users, songs, and
  ratings through the protected admin portal.
\end{enumerate}

\subsection{Non-functional requirements}
The application should be simple, responsive, compatible with MariaDB and MySQL, and configurable through environment variables. Queries use parameters, passwords are hashed, and uploaded filenames are handled safely.

\subsection{System architecture}
The browser renders Jinja templates and provides audio, rating, and
administration interactions. Flask handles routes, sessions, validation, and
file serving. MariaDB/MySQL stores users, songs, ratings, and administrator
status; audio files are stored in the configured upload directory.

\subsection{Entity-relationship model}
The database contains users, songs, and ratings. Users can upload songs and submit ratings; each song belongs to one uploader. The unique pair \texttt{(song\_id, user\_id)} allows one editable rating per user and song. The \texttt{song\_ratings\_summary} view provides average ratings and counts.

\subsection{Relational model}
The relational schema is represented by the following relations:
\begin{itemize}[leftmargin=*]
  \item \textbf{Users}(\underline{id}, username, password\_hash, is\_admin, created\_at)
  \item \textbf{Songs}(\underline{id}, uploader\_id, title, artist, filepath, uploaded\_at)
  \item \textbf{Ratings}(\underline{id}, song\_id, user\_id, stars, review\_text, created\_at)
\end{itemize}
Here, \texttt{uploader\_id} references \texttt{Users.id}, while
\texttt{song\_id} and \texttt{user\_id} reference the corresponding parent
relations in \texttt{Ratings}. The pair \texttt{(song\_id, user\_id)} is a
candidate key enforced by a unique constraint.

\subsection{Normalization}
The relations satisfy third normal form for the project data. Each table has
atomic attributes and a primary key, so it is in first normal form. Non-key
attributes depend on the whole key, avoiding partial dependencies. User,
song, and rating facts are separated, so non-key attributes do not depend on
other non-key attributes. Foreign keys connect the relations without
duplicating usernames, song metadata, or rating summaries.

\subsection{Implementation}

The Flask application in \texttt{app.py} retrieves songs, uploaders, and rating
aggregates with SQL. Registration validates fields and stores a Werkzeug
password hash. Login verifies the hash and stores the user identity in the
session. The protected admin portal provides dashboard statistics and
management pages for users, songs, and ratings. Administrator access is
controlled by the \texttt{users.is\_admin} column and checked on every admin
request.

The upload route uses \texttt{login\_required}, \texttt{secure\_filename}, and a user/random filename prefix. Rating submissions validate the song and star range, then use an upsert so repeated submissions update the existing row.

For databases created with an older schema, the administration feature
requires a one-time migration because \texttt{CREATE TABLE IF NOT EXISTS} does
not alter an existing \texttt{users} table:
\begin{lstlisting}[language=SQL]
ALTER TABLE users ADD COLUMN is_admin TINYINT(1) NOT NULL DEFAULT 0;
\end{lstlisting}
After the column exists, run the following Flask CLI command to create or
promote the first administrator:
\begin{lstlisting}[language=bash]
flask --app app create-admin
\end{lstlisting}

\subsubsection{Frontend}
Jinja templates extend \texttt{base.html}. The library displays song metadata, an HTML audio player, and rating summaries. \texttt{app.js} coordinates audio playback and submits ratings asynchronously. CSS media queries support smaller screens.

\subsection{Security and data integrity}
The implementation reduces common risks by using:
\begin{itemize}[leftmargin=*]
  \item Passwords are stored as hashes using Werkzeug rather than as plaintext.
  \item SQL values are passed as parameters to PyMySQL queries.
  \item Uploaded names are normalized with \texttt{secure\_filename}.
  \item Protected routes require a user ID in the session, and admin routes
  require the administrator flag.
  \item Foreign keys cascade removal of dependent songs and ratings.
  \item The database constrains stars to the range one to five.
  \item The unique rating key prevents duplicate ratings for one user and song.
  \item State-changing admin actions require a CSRF token.
\end{itemize}

Before deployment, the development secret key must be replaced. Upload size
and MIME type checks, moderation, and automated tests remain future
improvements.

\subsection{Limitations and future work}
Future work includes:
\begin{enumerate}[leftmargin=*]
  \item server-side file validation and stronger deployment configuration;
  \item search, sorting, pagination, and genre metadata;
  \item profiles, playlists, moderation, and richer administration features; and
  \item automated tests and production object storage.
\end{enumerate}
