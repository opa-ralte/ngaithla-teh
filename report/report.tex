\section{Abstract}
\projectname{} is a web-based community music library that allows users to create accounts, upload audio tracks, browse shared music, play tracks in the browser, and submit one editable star rating with an optional review for each song. The system was implemented using Flask and Python on the server, vanilla JavaScript and HTML/CSS in the browser, and MariaDB or MySQL for persistent storage. This report presents the system requirements, design, implementation, security considerations, testing approach, limitations, and possible future improvements.

\section{Introduction}

\subsection{Background}
Music sharing platforms can be complex and difficult to adapt for a small community. \projectname{} focuses on the essential interactions: sharing a track, listening to it, and receiving feedback from other members. The result is a deliberately small application with a clear user workflow and a relational database that preserves ownership and rating integrity.

\subsection{Aim and objectives}
The aim of the project is to provide a usable community music library with authenticated participation. The objectives are to:
\begin{itemize}[leftmargin=*]
  \item allow visitors to browse available songs and play audio in a web browser;
  \item allow new users to register and existing users to log in and log out;
  \item allow authenticated users to upload a song with a title and artist name;
  \item allow authenticated users to rate a song from one to five stars and add an optional review;
  \item prevent duplicate ratings from the same user for the same song; and
  \item store passwords and uploaded-file paths using safer application practices.
\end{itemize}

\subsection{Scope}
The implemented scope includes account management, song metadata, local audio storage, audio playback, aggregate ratings, reviews, and a responsive browser interface. Playlists, search, moderation, cloud storage, and administrative tools are outside the current scope.

\section{Requirements Analysis}

\subsection{Functional requirements}
\begin{enumerate}[leftmargin=*]
  \item A visitor shall be able to view the song library.
  \item A visitor shall be able to register with a unique username and password.
  \item A registered user shall be able to log in and log out.
  \item An authenticated user shall be able to upload a song title, artist name, and audio file.
  \item A visitor shall be able to play an uploaded song using the browser audio controls.
  \item An authenticated user shall be able to submit a one-to-five-star rating and optional review.
  \item A later rating submission shall update the user's existing rating for that song.
  \item The library shall show each song's average rating and rating count.
\end{enumerate}

\subsection{Non-functional requirements}
The application should be simple to use, responsive on smaller screens, compatible with MariaDB and MySQL, and configurable through environment variables. Database queries should use parameters, passwords should not be stored in plaintext, and uploaded filenames should be handled safely.

\section{System Design}

\subsection{Architecture}
The system follows a small three-layer web architecture. The browser renders server-side templates and supplies interactive rating behavior through JavaScript. Flask handles routes, sessions, validation, and file serving. MariaDB or MySQL stores users, songs, and ratings, while uploaded audio files are stored in the configured upload directory.

\subsection{Database design}
The database contains three primary entities. A user can upload many songs and submit many ratings. A song belongs to one uploader and can receive many ratings. The unique pair \texttt{(song\_id, user\_id)} ensures that each user has at most one rating for a particular song. The \texttt{song\_ratings\_summary} view provides a derived aggregate of average rating and rating count.

\section{Implementation}

\subsection{Backend}
The Flask application is implemented in \texttt{app.py}. The root route retrieves songs, uploader names, and aggregate ratings using a grouped SQL query. Registration validates required fields and stores a Werkzeug password hash. Login verifies the hash and stores the authenticated user's ID and username in the session.

The upload route is protected by the \texttt{login\_required} decorator. It uses \texttt{secure\_filename} and prefixes the stored filename with the user ID and a random value. Rating submissions accept JSON or form data, validate the star range, confirm that the song exists, and use an upsert operation so repeated submissions update the existing row.

\subsection{Frontend}
The interface uses Jinja templates extending \texttt{base.html}. The library page presents song metadata, an HTML audio player, the average rating, and the number of ratings. The JavaScript file provides two small interactions: only one audio player plays at a time, and rating forms allow star selection and asynchronous submission without reloading the page. CSS media queries provide a mobile layout for navigation, song cards, and rating panels.

\section{Security and Data Integrity}
Several implementation choices reduce common risks:
\begin{itemize}[leftmargin=*]
  \item Passwords are stored as hashes using Werkzeug rather than as plaintext.
  \item SQL values are passed as parameters to PyMySQL queries.
  \item Uploaded names are normalized with \texttt{secure\_filename}.
  \item Protected routes require a user ID in the session.
  \item Foreign keys cascade removal of dependent songs and ratings.
  \item The database constrains stars to the range one to five.
  \item The unique rating key prevents duplicate ratings for one user and song.
\end{itemize}

The current prototype also has important deployment limitations. The default development secret key must be replaced through configuration. There is no explicit upload size limit, MIME-type verification, CSRF protection, or moderation workflow. These should be addressed before exposing the application to untrusted users.

\section{Limitations and Future Work}
The project meets its core library requirements but can be extended in several practical directions:
\begin{enumerate}[leftmargin=*]
  \item Add server-side file-size and content-type validation.
  \item Add CSRF tokens to state-changing forms and requests.
  \item Add search, sorting, pagination, and genre metadata.
  \item Add user profiles, playlists, and track ownership management.
  \item Move audio storage to an object-storage service for production use.
  \item Add automated unit and integration tests to complement manual testing.
  \item Add administration and reporting tools for inappropriate content.
\end{enumerate}

\section{Conclusion}
\projectname{} provides a focused implementation of a community music library. Its Flask backend separates authentication, upload, playback, and rating responsibilities; its relational schema models ownership and feedback clearly; and its browser interface supports the essential listening workflow. The project is suitable as a working prototype and a foundation for future improvements in validation, moderation, search, testing, and deployment.
